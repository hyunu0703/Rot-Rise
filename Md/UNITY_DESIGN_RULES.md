# Unity C# 프로젝트 설계 및 구현 규칙

## 1. 객체지향 설계: SOLID

### 1.1 SRP — 단일 책임 원칙 (Single Responsibility Principle)

- 클래스는 하나의 응집된 책임과 주요 변경 이유를 가지도록 한다.
- 서로 독립적으로 변경되는 게임 규칙, UI, 입력, 연출, 저장 등을 분리한다.
- 하나의 책임에 속하는 관련 함수는 같은 클래스에 유지한다.
- 함수 하나마다 클래스를 생성하거나 책임이 명확한 작은 클래스까지 억지로 분리하지 않는다.
- God Class와 서로를 단순히 호출하기만 하는 과도한 클래스 분할을 모두 피한다.

### 1.2 OCP — 개방 폐쇄 원칙 (Open/Closed Principle)

- 무기, 스킬, 버프, 아이템, AI 등 실제로 여러 변형이 필요한 기능은 핵심 로직의 반복 수정 없이 확장할 수 있도록 설계한다.
- 데이터만 달라지는 기능은 데이터 정의로, 행동 규칙이 달라지는 기능은 컴포지션이나 Strategy 등의 적절한 방식으로 확장한다.
- 구현체 추가를 위한 등록/구성 변경은 허용한다.
- 일회성 기능이나 확장 가능성이 낮은 기능에 범용 프레임워크를 미리 만들지 않는다.
- OCP를 이유로 잘못된 기존 구조의 수정이나 버그 수정을 피하지 않는다.

### 1.3 LSP — 리스코프 치환 원칙 (Liskov Substitution Principle)

- 하위 타입은 상위 타입이 보장하는 동작 계약을 유지해야 한다.
- 하위 타입으로 대체해도 호출부의 예상 동작, 반환 규칙, 상태 조건이 깨지지 않아야 한다.
- 상속은 실제로 `is-a` 관계이며 공통 계약을 지킬 수 있을 때만 사용한다.
- 하위 타입에서 지원하지 않는 기능을 빈 구현이나 예외로 회피해야 한다면 상속 구조를 재검토한다.
- 공통 구현을 재사용하기 위한 목적만으로 상속하지 않는다. 컴포지션을 먼저 검토한다.

### 1.4 ISP — 인터페이스 분리 원칙 (Interface Segregation Principle)

- 호출자가 실제로 필요한 행동만 포함하도록 인터페이스를 설계한다.
- 서로 다른 객체가 동일한 행동 계약을 제공해야 할 때 인터페이스를 검토한다. 예: `IDamageable`, `IInteractable`.
- 객체가 사용하지 않는 메서드를 구현하도록 강제하지 않는다.
- 구현체가 하나뿐이고 교체, 테스트 경계, 결합도 감소의 이점이 없다면 불필요한 인터페이스를 만들지 않는다.
- 작은 인터페이스의 조합이 유용한 경우에만 분리한다. 모든 메서드를 별도 인터페이스로 분리하지 않는다.

### 1.5 DIP — 의존성 역전 원칙 (Dependency Inversion Principle)

- 핵심 게임 정책이 변하기 쉬운 구체적 구현에 직접 종속되지 않도록 필요한 경계에서 추상화한다.
- 교체 가능한 저장, 입력, 네트워크, 전투 대상 등은 실제 요구에 따라 공통 계약에 의존하도록 설계한다.
- 의존성은 Inspector 참조, 생성자, 명시적 초기화 등으로 전달한다.
- 일반 C# 클래스는 생성자 전달을 우선 검토하고, MonoBehaviour는 Unity 생명주기에 맞는 참조 전달을 사용한다.
- 변경 가능성이 낮은 단순 컴포넌트 참조는 직접 참조해도 된다.
- DIP와 의존성 주입을 동일한 개념으로 취급하지 않으며, 모든 클래스에 인터페이스나 DI 컨테이너를 도입하지 않는다.

## 2. 단순성 및 중복 관리

### 2.1 KISS — Keep It Simple, Stupid

- 요구사항을 충족하는 가장 단순하고 이해 가능한 구현을 선택한다.
- 필요 없는 Manager, Controller, Service, Factory, Wrapper 및 추상화 계층을 생성하지 않는다.
- 단순 기능은 직접 호출과 기본 제어문으로 충분한지 먼저 검토한다.
- 단순화 과정에서 필수 예외 처리와 상태 검증을 제거하지 않는다.

### 2.2 YAGNI — You Aren't Gonna Need It

- 현재 요구사항에 없고 확인되지 않은 미래 기능은 구현하지 않는다.
- 미래 확장을 이유로 사용하지 않는 클래스, 필드, API, 옵션, 이벤트를 미리 만들지 않는다.
- 이미 확정된 후속 요구사항과 변경 비용이 큰 핵심 경계는 필요한 범위에서 고려한다.

### 2.3 DRY — Don't Repeat Yourself

- 동일한 게임 규칙, 계산식, 상태 변경 규칙 및 데이터 정의를 여러 곳에 중복 구현하지 않는다.
- 변경 이유가 동일한 중복 로직은 적절한 공통 함수 또는 기존 시스템으로 통합한다.
- 코드 모양이 비슷하더라도 책임이나 변경 이유가 다른 코드는 무조건 합치지 않는다.

### 2.4 WET / AHA — 성급한 추상화 방지

- WET(Write Everything Twice 등) 및 AHA(Avoid Hasty Abstractions)의 취지에 따라 공통 규칙이 확인되기 전에 추상화하지 않는다.
- 작은 중복을 제거하려고 복잡한 상속, 조건문, 범용 함수, 타입 매개변수를 도입하지 않는다.
- 동일한 책임과 변경 패턴이 확인되면 DRY를 적용한다.
- 중복을 허용하더라도 핵심 게임 규칙이나 상태의 원본을 여러 곳에서 독립적으로 관리하지 않는다.

## 3. 책임, 클래스 관계 및 데이터 설계

### 3.1 Composition — 컴포지션 우선

- 상속보다 독립적인 컴포넌트와 객체 조합을 먼저 검토한다.
- 캐릭터의 이동, 체력, 공격 등 독립적인 행동은 재사용 가능한 컴포넌트로 구성할 수 있다.
- 하나의 자연스러운 책임을 필요 없이 여러 MonoBehaviour로 분리하지 않는다.
- 상속이 명확한 공통 계약과 단순한 구조를 제공한다면 제한적으로 사용한다.

### 3.2 High Cohesion / Low Coupling — 높은 응집도 / 낮은 결합도

- 같은 목적의 데이터와 동작을 같은 책임 경계에 모은다.
- 서로 관련 없는 기능은 별도 책임으로 관리한다.
- 클래스 간 필요한 최소한의 API만 공개하고 다른 클래스의 내부 구현에 의존하지 않는다.
- 이벤트나 인터페이스는 의존 관계를 실제로 개선할 때만 사용한다.
- 직접 호출이 자연스러운 관계를 과도한 이벤트 체인으로 변경하지 않는다.
- 순환 참조 및 여러 시스템의 숨겨진 상호 의존을 피한다.

### 3.3 SoC — 관심사 분리 (Separation of Concerns)

- 게임 규칙, 상태/데이터, 입력, UI, 연출, 저장의 책임을 구분한다.
- UI는 상태를 표시하고 입력 요청을 전달한다. 핵심 게임 규칙을 별도로 계산하거나 상태의 원본을 직접 소유하지 않는다.
- 연출은 게임 로직 결과를 시각화한다. 연출 변경만으로 게임 규칙이 변경되지 않도록 한다.
- 모든 기능에 별도 아키텍처 계층이나 MVC 구조를 강제하지 않는다.

### 3.4 Encapsulation — 캡슐화

- 상태는 해당 상태를 소유한 객체가 변경한다.
- 필드는 기본적으로 `private`으로 유지한다. Inspector 설정은 `[SerializeField] private`을 우선한다.
- 외부에서 상태를 읽어야 하면 필요한 최소한의 읽기 전용 API를 제공한다.
- 상태 변경은 `TakeDamage()`, `Heal()`, `TryAddItem()` 등 의미 있는 행동을 통해 수행한다.
- 상태 변경 시 필요한 유효성 검사와 후속 처리를 소유자 내부에서 보장한다.
- 외부에 수정 가능한 컬렉션이나 내부 상태를 불필요하게 노출하지 않는다.

### 3.5 SSOT — 단일 진실 공급원 (Single Source of Truth)

- HP, 아이템 수량, 턴, 게임 진행 상태 등 각 상태의 권위 있는 원본을 명확하게 지정한다.
- 동일 상태를 여러 시스템이 독립적으로 수정하지 않는다.
- UI, 연출, 저장용 스냅샷 및 캐시는 원본과 구분하고 필요한 갱신 규칙을 명시한다.
- ScriptableObject는 공유 설정 데이터로 우선 사용한다. 개별 객체의 실행 중 상태는 별도로 관리한다.
- 원본 변경은 정해진 API를 통해 수행하고 파생 데이터의 일관성을 유지한다.

### 3.6 LoD — 디미터 법칙 (Law of Demeter)

- 다른 객체의 내부 객체 관계나 깊은 데이터 구조에 과도하게 접근하지 않는다.
- 호출자가 내부 구조를 알아야 한다면 필요한 책임과 API를 재검토한다.
- 단순 데이터 조회나 Unity API 사용까지 기계적으로 래핑하지 않는다.

### 3.7 Tell, Don't Ask — 행동을 요청하라

- 객체 상태를 외부에서 조회한 후 그 객체의 내부 규칙을 대신 처리하지 않는다.
- 예: 외부에서 체력 감소 및 사망 판정을 각각 수행하지 말고 대상에게 피해 처리를 요청한다.
- 여러 객체의 관계를 판단하는 전투 조정자, UI 조회, 순수 데이터 객체 등 외부 판단이 자연스러운 경우는 허용한다.

### 3.8 Explicit Dependencies — 명시적 의존성

- 각 클래스가 필요로 하는 필수 참조와 초기화 조건을 코드 및 구성에서 명확하게 드러낸다.
- Inspector 참조, 생성자 또는 초기화 인자 전달을 우선 검토한다.
- 무분별한 Singleton, Service Locator, 전역 static 상태 및 반복적인 `Find*` 호출을 피한다.
- 전역 서비스가 실제로 필요한 경우 소유권과 생명주기를 명확히 한다.
- 필요한 참조를 한 번 확보하고 유효한 범위에서 재사용한다.

## 4. 예측 가능성과 안정성

### 4.1 POLA — 최소 놀람 원칙 (Principle of Least Astonishment)

- 클래스, 변수, 메서드 이름은 실제 책임과 동작을 나타낸다.
- 조회 함수가 예고 없이 게임 상태를 변경하지 않도록 한다.
- `Try*` 메서드는 예상 가능한 실패를 반환값으로 전달하고 호출자가 결과를 처리하게 한다.
- 동일한 API는 일관된 입력, 출력 및 상태 변경 규칙을 제공한다.
- 숨겨진 부작용과 불필요하게 복잡한 실행 흐름을 피한다.

### 4.2 Fail Fast — 잘못된 상태 조기 발견

- 필수 참조 누락, 중복 ID, 잘못된 설정값, 초기화 오류를 가능한 한 초기화 또는 데이터 로딩 단계에서 발견한다.
- 오류 원인과 관련 객체를 식별할 수 있는 메시지를 제공한다.
- 잘못된 필수 설정으로 시스템이 계속 실행되어 추가 오류를 발생시키지 않도록 한다.
- 일반적인 게임 플레이 실패(자원 부족, 빈 슬롯 등)는 예외가 아닌 정상적인 실패 결과로 처리한다.
- 오류를 숨기는 빈 catch, 무조건적인 null 무시, 의미 없는 기본값 대체를 피한다.
- 반복 실행 경로에서 과도한 로그를 남기지 않는다.

### 4.3 Avoid Premature Optimization — 성급한 최적화 방지

- 초기부터 불필요한 탐색, 할당, 중첩 반복을 피하고 적합한 자료구조를 선택한다.
- 복잡한 캐시, 풀링, 병렬 처리, ECS, Jobs/Burst 등은 실제 사용량과 병목 또는 명시된 요구사항에 따라 도입한다.
- Unity Profiler 등으로 측정할 수 있다면 측정 결과를 기준으로 최적화한다.
- 측정하지 않았다면 성능이 개선되었다고 단정하지 않는다.
- 최적화 이후에도 정확성, 상태 일관성, 가독성을 유지한다.

## 5. 원칙 충돌 시 판단 규칙

| 충돌 또는 상황 | 선택 기준 |
| --- | --- |
| SRP vs. KISS | 서로 다른 변경 책임이 있을 때 분리하고, 동일 책임은 유지한다. |
| OCP vs. YAGNI | 확정된 확장 또는 실제 반복 변경에 필요한 확장점만 만든다. |
| DRY vs. AHA/WET | 같은 모양이 아니라 같은 규칙과 변경 이유가 있는 경우에 통합한다. |
| DIP/ISP vs. 단순성 | 교체, 테스트, 공통 계약 또는 결합도 개선의 실익이 있을 때 추상화한다. |
| Composition vs. 상속 | 독립 행동의 조합은 컴포지션, 대체 가능한 공통 타입은 상속을 검토한다. |
| Low Coupling vs. 직접 호출 | 자연스러운 필수 의존은 명시적 직접 참조로 유지할 수 있다. |
| SSOT vs. 캐싱 | 원본 소유자를 유지하고 캐시 갱신 및 무효화 규칙을 명시한다. |
| 성능 vs. 가독성 | 기본적으로 단순한 구조를 유지하고 실제 병목 또는 필수 성능 제약에 한해 복잡성을 허용한다. |
| 코드량 vs. 안정성 | 검증, 상태 보호, 오류 처리, 필요한 책임 분리를 우선한다. |

설계 패턴, 인터페이스, 새 클래스 도입은 현재 해결할 문제와 도입 비용을 비교하여 결정한다. 실질적 이점이 없다면 도입하지 않는다.

## 6. 디자인 패턴 및 아키텍처 선택

패턴 이름에 맞춰 구조를 강제로 변경하지 않는다. 기존 구조를 먼저 확인하고 반복적으로 발생하는 문제에 적합한 패턴만 선택한다.

| 패턴 | 적용 조건 | 피해야 할 경우 |
| --- | --- | --- |
| State / FSM | 상태별 행동 및 전이 규칙이 복잡함 | 단순한 boolean 또는 enum 분기로 충분함 |
| Strategy | 동일 목적의 여러 행동 알고리즘을 교체해야 함 | 구현이 하나이며 변경 가능성이 낮음 |
| Observer / Event | 상태 변경을 여러 독립 시스템에 전달해야 함 | 단일 수신자 직접 호출이 자연스러움 |
| Command | 입력/행동을 큐잉, 재생, 취소하거나 기록해야 함 | 즉시 호출만 필요함 |
| Factory | 생성 규칙 및 구성 과정이 여러 곳에서 반복됨 | 단일 Prefab의 단순 Instantiate로 충분함 |
| Object Pool | 빈번한 생성/파괴로 할당, GC, 프레임 문제가 발생하거나 예상 사용량이 큼 | 생성 빈도가 낮고 관리 비용이 더 큼 |
| Component | 독립 행동을 여러 객체에 조합 및 재사용해야 함 | 하나의 응집된 책임을 인위적으로 분할함 |
| Event Queue | 처리 순서 및 시점 분리, 대기열 관리가 필요함 | 동기 호출이 충분하며 즉각 결과가 필요함 |
| MVC / MVP | UI와 게임 상태/표현 제어가 복잡하여 분리 이점이 큼 | 단순 UI에 여러 계층이 필요하지 않음 |
| Layered Architecture | 여러 시스템 경계와 의존성 방향을 명확히 해야 함 | 작은 기능에 형식적인 계층만 늘어남 |
| ECS | 대량 객체 처리 등 실제 데이터 처리 요구가 있고 도입 비용을 감당할 수 있음 | 일반 GameObject/Component 구조로 충분함 |

- Data-Driven Design: 아이템, 스킬, 적, 제작법 등 데이터 변형이 많은 기능은 ScriptableObject, 테이블 등 프로젝트에 맞는 데이터 정의를 활용한다. 모든 데이터를 외부 파일로 분리하지 않는다.
- Data-Oriented Design: 대량 반복 연산의 데이터 배치 및 메모리 접근 비용을 개선할 실익이 있을 때 검토한다. Data-Driven Design과 혼동하지 않는다.
- 리팩터링: 긴 함수, 중복 규칙, 잘못된 책임, 과도한 결합, 숨겨진 의존성 등 확인된 문제만 개선한다. 기능 변화 없는 리팩터링은 기존 외부 동작을 보존한다.
